סיפור פתיחה

קרב אש בגבול מצרים

בפרק מסדרת "מצפן מורשת" של חיל החינוך והנוער, מתאר מפקד חילופי אש בבטחון שוטף בגבול מצרים. במהלך הקרב, ברגע קריטי, הוא נדרש לאותת לכל הכוחות שהמצב הופך - בלי לחשוף בשידור הגלוי בדיוק מה קורה.

"בחילופי האש האלו אני מקבל דיווח, ואנחנו מכריזים מילת קוד. התכלית של הדבר הזה בבט"ש - זה להפוך את הקערה"

כל הכוחות בשטח יודעים מראש איזו מילה תיאמר וממה היא. ברגע שהיא נשמעת - כולם פועלים בו-זמנית.

ניתוח

למה זה עבד?

מילת הקוד היא בעצם סוד משותף שהוסכם עליו מראש (pre-shared secret) בין המפקד לכל הכוחות. מי שיודע את המילה - שייך ל"מעגל האמון". השידור עצמו לא צריך להיות מוצפן; מספיק שכולם כבר יודעים מה המילה אומרת.

זהו בעצם פרוטוקול אימות פרימיטיבי: המילה עצמה משמשת גם כ"זהות" (מי שאומר אותה שייך לצד שלנו) וגם כ"פקודה" (עכשיו!).

חשבו על זה רגע

מה קורה אם היריב שומע את המילה?

מילת קוד קבועה עובדת מצוין פעם אחת. אבל אם היא זהה בכל אירוע חוזר - כל מי שמיירט אותה פעם אחת יכול:

  • להתחזות (impersonation) - לשדר את אותה מילה בעצמו
  • לבצע replay attack - להשתמש שוב באותה מילה/אות בעתיד, גם ללא הבנה מלאה של המשמעות

בהקשר המבצעי הנקודתי (אירוע חד-פעמי, קצר) הסיכון נמוך יחסית - אבל ברגע שרוצים מערכת אימות שחוזרת על עצמה שוב ושוב (בין שרתים, בין מכשירים, בין מפקדות) - סוד קבוע שחוזר על עצמו הופך לנקודת כשל אמיתית. זה בדיוק המעבר שנעשה עכשיו: מהסיפור הנקודתי לעולם הדיגיטלי.

מהשדה למחשב

אותה בעיה בדיוק, בעולם הסייבר

מערכות דיגיטליות רבות נדרשות "לוודא מי אתה" שוב ושוב: שרת מול לקוח, שלט רכב מול הרכב, כרטיס עובד מול קורא כרטיסים.

דוגמה: שלט רכב ישן

שלט שמשדר תמיד את אותו קוד קבוע כדי לפתוח את הרכב - חשוף לתקיפת "תפוס ושדר שוב" (replay): תוקף מקליט את השידור פעם אחת, ומשמיע אותו שוב מתי שהוא רוצה.

הפתרון בעולם האמיתי (וגם ברכבים מודרניים, ב-SSH, ב-2FA) הוא אותו רעיון בדיוק שנצטרך עכשיו לבנות: לוודא בכל פעם מחדש, בלי לחזור על אותה תשובה פעמיים.

הפתרון

פרוטוקול אתגר-תגובה (Challenge-Response)

במקום להסתמך על סוד שנשלח כמו שהוא, המאמת שולח בכל פעם אתגר אקראי חדש, והצד השני צריך "להוכיח" שהוא מכיר את הסוד המשותף - בלי לחשוף אותו בעצמו.

מאמת: שולח אתגר אקראי (challenge)
←
מוכיח: מחשב תגובה = f(סוד, אתגר)
←
מאמת: משווה לתגובה שהוא ציפה לה

מכיוון שהאתגר שונה בכל פעם, גם התגובה תהיה שונה בכל פעם - גם אם הסוד תמיד אותו סוד.

הכלי המרכזי

HMAC - Hash-based Message Authentication Code

הפונקציה f מהשקף הקודם, בפועל, היא לרוב HMAC - שילוב של פונקציית hash (כמו SHA-256) עם מפתח סודי:

response = HMAC( secret_key , challenge )

hash רגיל (כמו sha256(challenge)) לא תלוי בסוד כלל - כל אחד יכול לחשב אותו, גם תוקף. הכוח של HMAC הוא שהתוצאה תלויה גם ב-secret_key שרק שני הצדדים המהימנים מכירים - כך שרק מי שמכיר את הסוד יכול לחשב את התגובה הנכונה לאתגר.

תכונות חשובות:

  • קל לחשב בכיוון אחד, בלתי-אפשרי (מבחינה חישובית) להפוך
  • שינוי קטן באתגר → תוצאה שונה לחלוטין (אפקט מפולת שלגים)
  • ללא ידיעת ה-secret_key, אי אפשר לנחש את התגובה הנכונה

ההגדרה הפורמלית (RFC 2104):

HMAC(K, m) = H( (K' ⊕ opad) || H( (K' ⊕ ipad) || m ) )

  • H - פונקציית ה-hash הבסיסית (למשל SHA-256)
  • K' - המפתח הסודי, מרופד (padded) או מכווץ באמצעות H כך שיתאים בדיוק לגודל ה-block של הפונקציה
  • ipad, opad - שני קבועים קבועים מראש (0x36 ו-0x5c, חוזרים לאורך כל ה-block), שתפקידם להבטיח שהמפתח "מעורבב" פנימה בשני אופנים שונים בשני סבבי hash נפרדים
  • || - שרשור (concatenation) של ביטים

הרעיון המרכזי: מריצים hash פעמיים (hash מקונן), עם שילוב שונה של המפתח בכל סבב. זה מגן מפני התקפות מסוימות שהיו אפשריות אם היו פשוט עושים H(K || m) ישירות (למשל, length-extension attacks בפונקציות hash מסוג Merkle-Damgård כמו SHA-256).

המרכיב השני

Nonce - ה"פעם הראשונה והאחרונה"

Nonce ("number used once") הוא ערך אקראי/עולה שנוצר מחדש בכל אימות - זה מה שהופך את מילת הקוד הקבועה מהסיפור ל"אתגר" שאינו חוזר על עצמו.

המאמת שומר (או בודק) שהאתגר בו נעשה שימוש לא הוצג בעבר. תגובה ל-nonce ישן - נדחית אוטומטית, גם אם היא "נכונה מתמטית" עבור אתגר קודם.

שילוב secret קבוע + nonce משתנה = בדיוק הפתרון לבעיה שזיהינו קודם עם מילת הקוד הקבועה בשדה.

הדגמת קוד · Python

מימוש אימות אתגר-תגובה עם HMAC

import hmac, hashlib, os

SHARED_SECRET = b"my-secret-key-both-sides-know"

def generate_challenge():
    return os.urandom(16)

def compute_response(challenge, secret=SHARED_SECRET):
    return hmac.new(secret, challenge, hashlib.sha256).hexdigest()

# צד המאמת (המפקד) שולח אתגר אקראי חדש
challenge = generate_challenge()

# צד המוכיח (החייל) מחשב תגובה מהסוד המשותף
response = compute_response(challenge)

# המאמת משווה לתגובה שהוא עצמו מצפה לה
expected = compute_response(challenge)
print(hmac.compare_digest(response, expected))  # True

# ניסיון replay: תגובה ישנה מול אתגר חדש - נכשל
new_challenge = generate_challenge()
print(hmac.compare_digest(response, compute_response(new_challenge)))  # False

== רגיל בפייתון משווה תווים אחד-אחד ועוצר ברגע שנמצא הבדל - זמן ההשוואה חושף מידע (timing attack, בדיוק כמו ב-HACKIT). hmac.compare_digest משווה בזמן קבוע, בלי לדלוף מידע דרך הזמן.

⏸ תחנת עצירה - עבודה עצמאית

עכשיו אתם: שברו את הפרוטוקול

עבדו בזוגות. קחו את הקוד מהשקף הקודם ושנו אותו כך ש:

  • הפרוטוקול משתמש ב-challenge קבוע (למשל תמיד b"1234567890123456") במקום אקראי
  • הריצו את הקוד פעמיים, ונסו "לגנוב" תגובה מהריצה הראשונה ולהשתמש בה בשנייה
  • תעדו: האם ה-replay הצליח? מה זה אומר על החשיבות של ה-nonce?

קריטריון הצלחה: קוד רץ בפועל + פסקה קצרה שמסבירה למה גרסה זו פגיעה יותר מהמקורית.

שימוש נכון ב-AI

פרוטוקול חשוב-כתוב-בדוק-שאל

חשוב - נסחו לבד את הרעיון: מה ההבדל בין הקוד המקורי לגרסה שביקשתי מכם לשבור, לפני שאתם פונים לכלי AI.

כתוב - נסו לממש את השינוי בעצמכם קודם.

בדוק - אם השתמשתם ב-AI לעזרה בתחביר/דיבוג - הריצו את הקוד בפועל ובדקו שההתנהגות תואמת את מה שציפיתם.

שאל - אם AI נתן לכם הסבר על HMAC/nonce - אתגרו אותו: "למה זה נכון? תן דוגמה נגדית".

⚠️ אזהרה: אל תעתיקו קוד מ-AI בלי להריץ ולהבין אותו שורה-שורה. במיוחד כאן - טעות קטנה (למשל השוואה עם == במקום compare_digest) יוצרת פגיעות אמיתית.

שאלות הבנה (1/2)

1. למה מילת קוד קבועה בשדה הקרב "עבדה" בסיפור, אבל תהיה בעייתית כמנגנון אימות דיגיטלי חוזר?

נכון: כשהסוד קבוע וחוזר, כל תיעוד/יירוט חד-פעמי מספיק כדי לחקות אותו לעד.

2. מה תפקידו העיקרי של ה-challenge בפרוטוקול אתגר-תגובה?

נכון: אתגר אקראי חדש מייצר תגובה חדשה בכל פעם - זה מה שמונע replay.

3. מדוע לא מספיק sha256(challenge) בלי מפתח סודי?

נכון: בלי מפתח, אין הבדל בין תגובה של הצד האמיתי לתגובה של תוקף - כל אחד יכול לחשב hash של ערך גלוי.
שאלות הבנה (2/2)

4. שיניתם את הקוד כך שה-challenge קבוע במקום אקראי. מה קורה לביטחון הפרוטוקול?

נכון: HMAC בעצמו לא מספיק - הוא צריך challenge שמשתנה כדי להגן מפני replay.

5. למה השתמשנו ב-hmac.compare_digest ולא ב-==?

נכון: השוואה בזמן קבוע מונעת דליפת מידע על נכונות תווים בודדים דרך מדידת זמן - בדיוק כמו ב-HACKIT.

6. תארו במילים שלכם: מה קורה אם מפקד וחייל שוכחים לתאם מראש את ה-secret_key?

אין תשובה "נכונה" יחידה - זו שאלה פתוחה לדיון: בלי סוד משותף שסוכם עליו מראש, אין בסיס לאימות כלל - הפרוטוקול כולו נשען על כך ששני הצדדים המהימנים, ורק הם, מחזיקים באותו secret_key.
