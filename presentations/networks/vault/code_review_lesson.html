מפתחים טוב יותר ביחד

איך הופכים קוד שעובד לקוד שאפשר לסמוך עליו?

היום נלמד לבדוק קוד של חבר, לתת משוב מקצועי ולשפר פתרון לפני שילובו במערכת.

1 | האם קוד שעובד הוא קוד טוב?

def receive_message(sock):
    return sock.recv(1024).decode('utf-8')

בבדיקה אחת התקבלה ההודעה HELLO. האם אפשר לאשר את הקוד?

בדיקה מוצלחת אינה מוכיחה שהקוד עומד בחוזה התקשורת. יש להשתמש ב־framing ולקרוא את מספר הבתים הנדרש לפני פענוח.

2 | מהי סקירת קוד?

חבר צוות קורא שינוי בקוד של מפתח אחר, בוחן אותו מול הדרישות ומציע שיפורים מנומקים.

המפתח

מסביר מה השתנה, מדוע ואילו בדיקות ביצע.

הסוקר

קורא, שואל, בודק ומציע תיקונים.

שניהם

מסכימים על השינויים, בודקים מחדש ומתעדים.

סקירה אינה מבחן אישי ואינה תחליף לבדיקות תוכנה. היא בדיקה של הקוד ושל ההחלטות ההנדסיות.

3 | תהליך העבודה

אם הבדיקה נכשלת, חוזרים לתיקון ולסקירה. לא חייבים לקבל כל הצעה, אך יש לנמק החלטות.

4 | מה בודקים?

נכונות

האם הדרישות מתקיימות?

קריאות

שמות, חלוקה לפונקציות ובהירות.

ארכיטקטורה

האם האחריות נמצאת במחלקה המתאימה?

אמינות

ניתוקים, חריגות ומקרי קצה.

סנכרון

גישה למשאבים משותפים ומנעולים.

בדיקות

האם קיימות ראיות שהשינוי פועל?

5 | דוגמה: טיפול בחריגות

try:
    process_request()
except Exception:
    pass

כתבו הערת סקירה: מה הבעיה, מה ההשפעה ומה כדאי לשנות?

חריגות בלתי צפויות נעלמות ולכן קשה לאתר תקלות. כדאי לטפל בחריגות צפויות בנפרד ולתעד חריגות אחרות. למשל, בגבול הטיפול בבקשה:
try:
    process_request()
except ConnectionError as exc:
    logging.info('Client disconnected: %s', exc)
except Exception:
    logging.exception('Unexpected request failure')
    raise
יש להחליט בשכבה הקוראת כיצד לסגור את החיבור; logging מיובא מראש.

6 | דוגמה: משאב משותף

def remove_handler(self, handler):
    if handler in self.handlers:
        self.handlers.remove(handler)

שני Threads עשויים לבצע את הפעולה באותו זמן. מה חסר?

def remove_handler(self, handler):
    with self.lock:
        if handler in self.handlers:
            self.handlers.remove(handler)
כל הגישות הרלוונטיות לרשימה צריכות להשתמש באותו מנעול. אין להחזיק אותו בזמן פעולת רשת חוסמת.

7 | דוגמה: קריאת TCP

def recv_exact(sock, n):
    data = sock.recv(n)
    return data

בחרו את הערת הסקירה המתאימה ביותר.

def recv_exact(sock, n):
    data = bytearray()
    while len(data) < n:
        chunk = sock.recv(n - len(data))
        if not chunk:
            raise EOFError('Connection closed')
        data.extend(chunk)
    return bytes(data)
החוזה בדוגמה: ניתוק לפני השלמת הקריאה גורם לחריגה. יש להתאים את הטיפול בה לשאר הפרוטוקול.

8 | משוב מקצועי ולא אישי

משוב לא מועיל

״הקוד שלך גרוע. תתקן.״

משוב מועיל

״בפעולת recv ייתכן שיתקבלו פחות בתים מהנדרש. כדאי להוסיף לולאת קריאה ובדיקה לניתוק.״

תבנית: מיקום → ממצא → השפעה → הצעה → בדיקה.

בפעולת remove_handler הבדיקה וההסרה אינן מוגנות באותו מנעול. האם אפשר לעטוף אותן ב־with lock ולבדוק שני ניתוקים מקבילים?

9 | סקירת קוד ב־GitHub

אפשר לבצע סקירה גם ללא GitHub. כאשר עובדים עם branches, Pull Request מאפשר לרכז את השינוי ואת המשוב.

1. המפתח דוחף branch ופותח Pull Request.
2. הסוקר פותח Files changed וקורא את השינויים.
3. מוסיף הערות לשורות רלוונטיות ובוחר Submit review.
4. המפתח מגיב, מתקן ומעלה commit נוסף.
5. לאחר בדיקות וסקירה חוזרת, מאשרים ומשלבים לפי כללי הקבוצה.

Approve = אישור; Request changes = בקשת תיקונים; Comment = משוב ללא אישור או חסימה.

10 | תרגול: אתם הסוקרים

def request(self, message):
    with self.lock:
        Protocol.send(self.sock, message)
    return Protocol.receive(self.sock)

הניחו ששני Threads משתמשים באותו לקוח. מצאו ליקוי, הסבירו תרחיש שבו הוא מתרחש, הציעו תיקון ובדיקה.

המנעול משתחרר לפני קבלת התשובה. Thread אחר עלול לשלוח בקשה ולקרוא תשובה שאינה שלו. יש להגן על רצף השליחה והקבלה כולו:
def request(self, message):
    with self.lock:
        Protocol.send(self.sock, message)
        return Protocol.receive(self.sock)
בדיקה: שתי בקשות ECHO שונות מאותו לקוח במקביל, פעמים רבות, ולוודא שכל תשובה מתאימה לבקשה שלה.
