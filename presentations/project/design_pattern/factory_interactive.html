Factory Design Pattern

בסיום תוכלו לזהות צורך ב־Factory, לממש Simple Factory ולהבחין בינו לבין Factory Method.

1. מהי תבנית עיצוב?

Design Pattern היא דרך מוכרת לארגון פתרון לבעיה חוזרת בתכנון תוכנה — לא קוד שמעתיקים אוטומטית.

בעיה חוזרת

קוד שתלוי בסוגים קונקרטיים רבים

עיקרון

הפרדת אחריות יצירת אובייקטים

תוצאה

קוד לקוח פשוט יותר לשינוי ולבדיקה
שאלת פתיחה: האם כל שימוש ב־if הוא בעיית תכנון?
לא. תנאים הם כלי חיוני. הבעיה מתחילה כשאותה החלטת יצירה מפוזרת במקומות רבים, או כשקוד הלקוח מכיר יותר מדי מחלקות.

2. סיפור: מרכז ניטור סייבר

שרת מקבל התראות LOGIN_FAILED, PORT_SCAN ו־MALWARE. כל אירוע צריך לעבור ניתוח שונה.

📡 אירוע נכנס ← 🖥️ שרת ← 🔍 ניתוח

מחר יתווספו סוגי אירועים חדשים. כיצד נוודא שהקוד שקורא ל־analyze() לא יצטרך להכיר כל מחלקה?

3. קוד ראשוני — מצאו את הבעיה

def handle_event(event_type):
    if event_type == "LOGIN_FAILED":
        event = LoginFailedEvent()
    elif event_type == "PORT_SCAN":
        event = PortScanEvent()
    elif event_type == "MALWARE":
        event = MalwareEvent()
    else:
        raise ValueError("Unknown type")
    return event.analyze()

מה יקרה אם אותה לוגיקה קיימת גם בשרת, גם בסקריפט בדיקות וגם בכלי ניהול?

ניאלץ לעדכן כמה מקומות בכל הוספת סוג. הלקוח אחראי גם להחליט איזו מחלקה ליצור וגם להפעיל אותה. עם זאת, במקרה קטן עם מקום יצירה יחיד ייתכן שהקוד הזה מספיק טוב.

4. בחרו פתרון

כעת יש 12 סוגי אירועים ושלושה רכיבים שיוצרים אותם. איזו גישה מתאימה ביותר?

5. הרעיון של Simple Factory

Client → EventFactory.create_event(type)
↓
LoginFailedEvent
PortScanEvent
MalwareEvent

הלקוח מבקש אובייקט לפי סוג, ומקבל אובייקט בעל ממשק משותף. ה־Factory מחליט איזו מחלקה קונקרטית ליצור.

Simple Factory הוא שם מקובל לאידיום תכנון; הוא אינו זהה ל־Factory Method הקלאסי.

6. חוזה משותף באמצעות ABC

from abc import ABC, abstractmethod

class SecurityEvent(ABC):
    @abstractmethod
    def analyze(self):
        pass

class LoginFailedEvent(SecurityEvent):
    def analyze(self):
        return "Analyze failed logins"

class PortScanEvent(SecurityEvent):
    def analyze(self):
        return "Analyze port scans"

המחלקות הקונקרטיות מממשות את אותו ממשק. כך הלקוח יכול לקרוא ל־analyze() בלי לבדוק שוב את סוג האירוע.

7. מימוש Factory

class EventFactory:
    @staticmethod
    def create_event(event_type: str) -> SecurityEvent:
        if event_type == "LOGIN_FAILED":
            return LoginFailedEvent()
        if event_type == "PORT_SCAN":
            return PortScanEvent()
        raise ValueError(f"Unknown event: {event_type}")

# Client code
event = EventFactory.create_event("PORT_SCAN")
print(event.analyze())
מי אחראי על מה?

Factory: יצירה ובחירת מחלקה. Event: התנהגות וניתוח. Client: שימוש בממשק המשותף.

8. הדגמה אינטראקטיבית

בחרו אירוע כדי לראות איזו מחלקה נוצרת ומה מחזירה הפעולה analyze().

ההדגמה ממחישה את התנהגות הקוד; היא אינה מריצה Python בדפדפן.

9. אתגר: הוספת סוג חדש

נדרש אירוע BRUTE_FORCE. מה צריך לשנות?

  1. מחלקה חדשה שמממשת analyze().
  2. מיפוי מתאים ב־Factory.
  3. בדיקה שהלקוח מסוגל להשתמש באובייקט.
class BruteForceEvent(SecurityEvent):
    def analyze(self):
        return "Analyze brute-force attempts"

# Add to create_event:
if event_type == "BRUTE_FORCE":
    return BruteForceEvent()
שימו לב: ב־Simple Factory מבוסס if עדיין צריך לשנות את ה־Factory כשמוסיפים סוג.

10. לפני ואחרי

ללא Factory

if kind == "PORT_SCAN":
    obj = PortScanEvent()
else:
    obj = LoginFailedEvent()
obj.analyze()

עם Factory

obj = EventFactory.create_event(kind)
obj.analyze()

ההבדל החשוב אינו מספר השורות אלא מיקום האחריות. יצירה מרוכזת, שימוש מופרד.

תרשים מחלקות UML — Simple Factory

התרשים מציג את המחלקות במערכת ניטור אירועי סייבר, את הירושה ואת הקשר בין הלקוח למפעל היוצר אובייקטים. שימו לב: ה־Factory מקבל גם event_type וגם source_ip ו־severity.

חץ משולש חלול

ירושה: PortScanEvent ו־LoginFailedEvent יורשות מ־SecurityEvent.

חץ מקווקו

תלות או יצירה: הלקוח משתמש ב־Factory, וה־Factory בוחר מחלקה קונקרטית.

שאלת הבנה: האם ה־Factory מחזיר את המחלקה PortScanEvent או מופע שלה? ולאן מועברים source_ip ו־severity?
ה־Factory מחזיר מופע של מחלקה קונקרטית, למשל PortScanEvent(source_ip, severity). הפרמטרים מועברים לבנאי ומאתחלים את האובייקט. קוד הלקוח עובד מול הממשק המשותף SecurityEvent.

11. Factory מקבל גם פרמטרים!

עד עכשיו ה־Factory קיבל רק את event_type. בפועל הוא יכול לקבל גם נתונים הדרושים לבנאי של האובייקט.

Client → Factory(type, source_ip, severity)
↓
PortScanEvent(source_ip, severity)
class PortScanEvent(SecurityEvent):
    def __init__(self, source_ip, severity):
        self.source_ip = source_ip
        self.severity = severity

    def analyze(self):
        return f"Port scan from {self.source_ip}: {self.severity}"

שאלת חשיבה: איזה פרמטר קובע איזו מחלקה ליצור, ואילו פרמטרים קובעים את מצב האובייקט?

event_type בוחר מחלקה. source_ip ו־severity מועברים לבנאי ומאתחלים את האובייקט.

12. Factory עם פרמטרים מפורשים

class LoginFailedEvent(SecurityEvent):
    def __init__(self, source_ip, severity):
        self.source_ip = source_ip
        self.severity = severity

    def analyze(self):
        return f"Login failure: {self.source_ip} ({self.severity})"

class EventFactory:
    @staticmethod
    def create_event(event_type, source_ip, severity):
        if event_type == "LOGIN_FAILED":
            return LoginFailedEvent(source_ip, severity)
        if event_type == "PORT_SCAN":
            return PortScanEvent(source_ip, severity)
        raise ValueError(f"Unknown event: {event_type}")

event = EventFactory.create_event(
    "PORT_SCAN", "192.0.2.10", "HIGH"
)
print(event.analyze())
נקודת מפתח: שני הסוגים בדוגמה מקבלים את אותם פרמטרים. לכן חתימה מפורשת ברורה וקלה לבדיקה. ה־Factory אינו חייב לקבל רק מחרוזת סוג.

13. הדמיה: צרו אירוע עם נתונים

בחרו סוג, כתובת מקור ורמת חומרה. בדקו כיצד הפרמטרים עוברים דרך ה־Factory לבנאי.

בחרו פרמטרים ולחצו על יצירה.

ההדגמה מציגה את משמעות הקריאה בפייתון; הקוד אינו מורץ בדפדפן.

14. כשלכל מחלקה פרמטרים שונים: **kwargs

למשל, התראת דוא״ל דורשת email והתראת SMS דורשת phone. אפשר להעביר ארגומנטים בשם באמצעות **kwargs.

class EmailAlert:
    def __init__(self, email, message):
        self.email = email
        self.message = message

class SMSAlert:
    def __init__(self, phone, message):
        self.phone = phone
        self.message = message

class AlertFactory:
    TYPES = {"email": EmailAlert, "sms": SMSAlert}

    @classmethod
    def create(cls, kind, **kwargs):
        alert_class = cls.TYPES.get(kind)
        if alert_class is None:
            raise ValueError("Unknown alert type")
        return alert_class(**kwargs)

alert = AlertFactory.create(
    "email", email="a@example.com", message="Warning"
)
שגיאת כתיב או פרמטר חסר, למשל emial=..., עלולים לגרום ל־TypeError בזמן ריצה. מומלץ להעדיף חתימה מפורשת כשאפשר, ולשלב ולידציה ובדיקות כאשר משתמשים ב־**kwargs.

15. אתגר: מצאו את התקלה

class AlertFactory:
    TYPES = {"email": EmailAlert, "sms": SMSAlert}

    @classmethod
    def create(cls, kind, **kwargs):
        return cls.TYPES[kind](**kwargs)

alert = AlertFactory.create(
    "sms", email="a@example.com", message="Warning"
)

האם ייווצר אובייקט? מה יקרה ומדוע?

16. מתי לבחור כל דרך?

פרמטרים מפורשים

כשהבנאים דומים או כשהחוזה צריך להיות ברור.

create_event(kind, ip, severity)
יתרון: קריאות, השלמה אוטומטית ובדיקות טיפוסים.

**kwargs

כשלסוגים שונים יש בנאים שונים, ורוצים מנגנון יצירה גמיש.

create_alert(kind, **kwargs)
מחיר: נדרש תיעוד, ולידציה וטיפול בשגיאות.
משימת יישום: הוסיפו ל־Factory של שרת הכספת פרמטר request_id המועבר לכל Handler. האם יש צורך לשנות את קוד הלקוח שמפעיל handle()?
אפשר להשאיר את קריאת handle(request) ללא שינוי. צריך לעדכן את חתימת ה־Factory ואת הבנאים הרלוונטיים, ולהעביר request_id בזמן היצירה. אם קוד הלקוח קורא ל־Factory, הוא יצטרך לספק את הפרמטר החדש או לקבל ברירת מחדל מתאימה.

11. מתי כדאי לבחור Factory?

  • סוג האובייקט נקבע בזמן ריצה לפי בקשה, קונפיגורציה או פרוטוקול.
  • יש כמה מחלקות בעלות ממשק משותף.
  • אותה לוגיקת יצירה חוזרת במקומות שונים.
  • ליצירה יש שלבים מורכבים שראוי להסתיר מהלקוח.
שאלת החלטה: האם אני רוצה שהקוד המשתמש ידע מה לעשות עם האובייקט, בלי לדעת איך ליצור אותו?

12. מתי Factory מיותר?

בפרויקט יש מחלקה אחת Logger, והקוד יוצר אותה פעם אחת במקום מוגדר. האם צריך Factory?

13. Simple Factory לעומת Factory Method

Simple Factory

פונקציה או מחלקה מרכזית בוחרת סוג באמצעות פרמטר.

EventFactory.create_event(kind)

Factory Method

מחלקת בסיס מגדירה מתודת יצירה; תתי־מחלקות מחליטות איזה מוצר קונקרטי להחזיר.

class Creator(ABC):
    @abstractmethod
    def create_event(self): ...

נתחיל ב־Simple Factory כי הוא ממחיש היטב הפרדת אחריות; לאחר מכן אפשר להרחיב ל־Factory Method.

14. אתגר שרת–לקוח

שרת כספת מקבל בקשות UPLOAD, DOWNLOAD, DELETE. תכננו:

  1. ממשק RequestHandler עם מתודה handle(request).
  2. שלוש מחלקות טיפול נפרדות.
  3. HandlerFactory.create_handler(action).
  4. טיפול בפקודה לא מוכרת.
הפרידו בין ניתוח סוג הבקשה לבין ביצוע הפעולה. ה־Factory יוצר Handler; השרת מפעיל handler.handle(request). בדיקות הרשאה חייבות להתבצע בשרת ולא להסתמך על סוג האובייקט בלבד.
