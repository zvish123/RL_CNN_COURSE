כיתה י״א סייבר · 24 משימות · 4 שאלות הבנה · רפלקציה

איך עובדים עם המדריך?

נסו לפתור, פתחו רמז ורק אז חשפו את הפתרון. הריצו את השאילתות לפי הסדר ב-SQLite.

קובץ בסיס הנתונים המקורי לא צורף. השאילתות נבדקו על בסיס נתונים סינתטי לפי הסכימה, ולא על נתוני התלמידים. תוצאות שאינן ידועות מתוארות כתנאי בדיקה. הנחת עבודה: מזהי INTEGER PRIMARY KEY נוצרים אוטומטית. הפעילו PRAGMA foreign_keys = ON; בכל חיבור. שמרו עותק לפני שינויים ואל תריצו INSERT שוב ללא איפוס.

מבנה בסיס הנתונים – סכימה (Schema)

שלוש הטבלאות מקושרות באמצעות מפתחות ראשיים (PK) ומפתחות זרים (FK). קובץ שייך לבעלים אחד, אך ניתן לשתף אותו עם משתמשים רבים דרך טבלת ההרשאות.

טבלהתפקידקשרים ואילוצים
usersפרטי חשבונות המשתמשיםid מפתח ראשי; username ייחודי
filesמטא־דאטה של קבצים ובעליהםowner_id → users.id
file_permissionsהרשאות שהוענקו למשתמשיםfile_id → files.id; user_id → users.id; הצירוף (file_id, user_id) ייחודי
הסבר השדות וכללי העבודה

id מזהה רשומה; owner_id בעל הקובץ; file_id הקובץ המשותף; user_id המשתמש שקיבל הרשאה. שדות can_view, can_download, can_edit, can_delete מקבלים 1 (כן) או 0 (לא). is_active מציין אם החשבון פעיל. storage_path הוא נתיב פנימי ולא תוכן הקובץ. ערכי password_hash בקובץ התרגול הם ערכי דמה, ולא גיבובים אמיתיים.

הקשרים: משתמש אחד יכול להיות בעלים של קבצים רבים; לכל קובץ יכולות להיות הרשאות רבות; כל רשומת הרשאה מתייחסת למשתמש אחד ולקובץ אחד.

שימו לב: הרשאות השיתוף הן רשומות מפורשות. בעל הקובץ אינו חייב להופיע בטבלת file_permissions כדי להיחשב בעליו.

חשיפת פתרון והסבר

סננו לפי is_active

חשיפת פתרון והסבר

הסבר: WHERE מסנן חשבונות פעילים; SELECT מחזיר רק את השם.

תוצאה ובדיקה: רק שמות חשבונות פעילים.

א3. הציגו קבצים שגודלם מעל 1,000,000 בתים.

חשיפת פתרון והסבר

הסבר: האופרטור > אינו כולל קובץ בגודל מיליון בדיוק.

תוצאה ובדיקה: כל קובץ גדול ממיליון בתים.

א4. הציגו את כל הקבצים של משתמש מספר 2.

חשיפת פתרון והסבר

הסבר: owner_id הוא מזהה הבעלים, לא מזהה הקובץ.

תוצאה ובדיקה: רק קבצים בבעלות משתמש 2.

הסבר: ORDER BY ממיין; NOCASE מתעלם מהבדלי אותיות ASCII גדולות וקטנות.

תוצאה ובדיקה: שמות בסדר עולה.

הסבר: COUNT סופר שורות ומחזיר ערך יחיד.

שלב ב – הוספת נתונים – INSERT

ב1. הוסיפו משתמש בשם cyber_student עם ערך גיבוב דמה לתרגול.

רמז

ציינו עמודות וערכים

חשיפת פתרון והסבר
INSERT INTO users (username, password_hash, is_active, created_at)
VALUES ('cyber_student', 'dummy_hash', 1, CURRENT_TIMESTAMP);

הסבר: מציינים עמודות וערכים בהתאמה. מניחים שמזהה נוצר אוטומטית. הגיבוב הוא דמה בלבד.

תוצאה ובדיקה: משתמש חדש אחד; 7 משתמשים אם לא בוצעו שינויים נוספים.

ב2. הוסיפו למשתמש החדש קובץ secret_report.pdf עם נתיב אחסון ייחודי.

רמז

אתרו בעלים לפי שם

חשיפת פתרון והסבר
INSERT INTO files (owner_id, original_name, storage_path, size_bytes, uploaded_at, updated_at)
VALUES ((SELECT id FROM users WHERE username = 'cyber_student'), 'secret_report.pdf', '/vault/cyber_student_report.enc', 2500000, CURRENT_TIMESTAMP, CURRENT_TIMESTAMP);

הסבר: שאילתת משנה מאתרת את מזהה המשתמש לפי שם ייחודי. הנתיב והגודל נבחרו לדוגמה; אין להניח שהמזהה הוא 7.

תוצאה ובדיקה: קובץ חדש אחד בבעלות המשתמש החדש; אין כאן יצירת קובץ פיזי.

ב3. העניקו למשתמש 3 הרשאות צפייה והורדה לקובץ החדש, ללא עריכה ומחיקה.

רמז

אתרו קובץ לפי נתיב

חשיפת פתרון והסבר
INSERT INTO file_permissions (file_id, user_id, can_view, can_download, can_edit, can_delete, granted_at)
VALUES ((SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc'), 3, 1, 1, 0, 0, CURRENT_TIMESTAMP);

הסבר: מאתרים את הקובץ לפי נתיב ייחודי. ארבעת הדגלים מגדירים הרשאות נפרדות.

תוצאה ובדיקה: הרשאה אחת עם הדגלים 1,1,0,0.

ב4. בדקו שהרשומות נוספו באמצעות שאילתות SELECT.

רמז

בדקו את שלוש הטבלאות

חשיפת פתרון והסבר
SELECT id, username, is_active FROM users WHERE username = 'cyber_student';
SELECT * FROM files WHERE id = (SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc');
SELECT * FROM file_permissions WHERE file_id = (SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc') AND user_id = 3;

הסבר: שלוש שאילתות בודקות כל טבלה בנפרד ואת המזהים המקשרים.

תוצאה ובדיקה: רשומה אחת בכל שאילתה לאחר שלב ב.

שלב ג – עדכון ומחיקה – UPDATE / DELETE

ג1. שנו את שם הקובץ החדש ל־final_report.pdf.

רמז

סננו לפי מזהה ייחודי

חשיפת פתרון והסבר
UPDATE files SET original_name = 'final_report.pdf', updated_at = CURRENT_TIMESTAMP
WHERE id = (SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc');

הסבר: משנים את שם התצוגה בלבד ולא את נתיב האחסון.

תוצאה ובדיקה: רק הקובץ החדש משנה שם.

ג2. בטלו למשתמש 3 את הרשאת ההורדה לקובץ החדש.

רמז

סננו לפי קובץ ומשתמש

חשיפת פתרון והסבר
UPDATE file_permissions SET can_download = 0
WHERE file_id = (SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc') AND user_id = 3;

הסבר: שני תנאים מזהים הרשאה מסוימת. שאר הדגלים אינם משתנים.

תוצאה ובדיקה: דגלים 1,0,0,0 לפני ג4.

ג3. הפכו את משתמש מספר 5 ללא פעיל (ייתכן שהוא כבר לא פעיל בנתוני הפתיחה).

רמז

סננו לפי id

חשיפת פתרון והסבר
UPDATE users SET is_active = 0 WHERE id = 5;

הסבר: מעדכנים רק חשבון אחד. אם כבר לא פעיל, הערך נשאר 0.

תוצאה ובדיקה: משתמש 5 אינו פעיל; הרשאותיו אינן נמחקות אוטומטית.

ג4. מחקו את הרשאת השיתוף של משתמש 3 לקובץ החדש.

רמז

מחקו רק את הצמד

חשיפת פתרון והסבר
DELETE FROM file_permissions WHERE file_id = (SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc') AND user_id = 3;

הסבר: מוחקים רשומת שיתוף ולא את הקובץ או המשתמש.

תוצאה ובדיקה: אין עוד הרשאה מפורשת למשתמש 3 בקובץ החדש.

ג5. כתבו שאילתת בדיקה שתוכיח שהשינויים השפיעו רק על הרשומות הרצויות.

רמז

השוו למצב לפני השינוי

חשיפת פתרון והסבר
SELECT * FROM files WHERE id = (SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc');
SELECT * FROM users WHERE id = 5;
SELECT * FROM file_permissions WHERE file_id = (SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc') AND user_id = 3;
SELECT id, original_name, updated_at FROM files WHERE id <> (SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc');
SELECT id, is_active FROM users WHERE id <> 5;
SELECT * FROM file_permissions WHERE NOT (file_id = (SELECT id FROM files WHERE storage_path = '/vault/cyber_student_report.enc') AND user_id = 3);

הסבר: בודקים את הרשומות הרצויות ומשווים את יתר הרשומות לצילום מצב לפני שלב ג. ללא צילום מצב אי אפשר להוכיח שלא השתנו. יש לבדוק את ג2 מיד לאחר ביצועה, לפני ג4.

תוצאה ובדיקה: שם חדש, משתמש 5 לא פעיל, אפס הרשאות לצמד; יתר הרשומות זהות לצילום המצב.

שלב ד – חיבור טבלאות – JOIN

ד1. הציגו שמות קבצים ושמות בעליהם.

רמז

חברו owner_id ל-id

חשיפת פתרון והסבר
SELECT f.original_name, u.username AS owner
FROM files AS f JOIN users AS u ON f.owner_id = u.id;

הסבר: JOIN מחבר כל קובץ לבעליו באמצעות המפתח הזר.

תוצאה ובדיקה: שורה לכל קובץ עם שם בעליו.

ד2. הציגו את הקבצים המשותפים עם משתמש מספר 3.

רמז

התחילו בטבלת ההרשאות

חשיפת פתרון והסבר
SELECT f.id, f.original_name
FROM file_permissions AS p JOIN files AS f ON p.file_id = f.id
WHERE p.user_id = 3 AND (p.can_view = 1 OR p.can_download = 1 OR p.can_edit = 1 OR p.can_delete = 1);

הסבר: מחפשים שיתוף מפורש למשתמש 3 עם לפחות פעולה מותרת אחת. אם רוצים כל רשומת שיתוף, אפשר להשמיט את תנאי הדגלים.

תוצאה ובדיקה: קבצים משותפים למשתמש 3; הקובץ החדש אינו מופיע אחרי ג4.

ד3. הציגו שם קובץ, שם בעלים, שם מקבל הרשאה וסוגי הרשאות.

רמז

השתמשו בשני כינויים ל-users

חשיפת פתרון והסבר
SELECT f.original_name, o.username AS owner, u.username AS recipient,
       p.can_view, p.can_download, p.can_edit, p.can_delete
FROM file_permissions AS p
JOIN files AS f ON p.file_id = f.id
JOIN users AS o ON f.owner_id = o.id
JOIN users AS u ON p.user_id = u.id;

הסבר: מחברים users פעמיים בכינויים שונים: בעלים ומקבל הרשאה.

תוצאה ובדיקה: שורה לכל רשומת הרשאה.

ד4. הציגו משתמשים שקיבלו הרשאת מחיקה על קובץ שאינו בבעלותם.

רמז

השוו בעלים למקבל

חשיפת פתרון והסבר
SELECT DISTINCT u.id, u.username
FROM file_permissions AS p
JOIN files AS f ON p.file_id = f.id
JOIN users AS u ON p.user_id = u.id
WHERE p.can_delete = 1 AND p.user_id <> f.owner_id;

הסבר: משווים את מקבל ההרשאה לבעלים; DISTINCT מונע כפילות משתמשים.

תוצאה ובדיקה: משתמשים בעלי הרשאת מחיקה לקובץ זר.

ד5. מצאו משתמשים שלא קיבלו הרשאה לאף קובץ.

רמז

חפשו NULL אחרי LEFT JOIN

חשיפת פתרון והסבר
SELECT u.id, u.username FROM users AS u
LEFT JOIN file_permissions AS p ON u.id = p.user_id
WHERE p.id IS NULL;

הסבר: LEFT JOIN שומר גם משתמשים ללא התאמה; NULL מזהה היעדר רשומת הרשאה. בעלות אינה שיתוף.

תוצאה ובדיקה: משתמשים ללא רשומות הרשאה מפורשות.

שלב ה – חקירת אבטחה

ה1. מצאו משתמשים לא פעילים שעדיין מחזיקים בהרשאות.

רמז

סננו is_active

חשיפת פתרון והסבר
SELECT DISTINCT u.id, u.username
FROM users AS u JOIN file_permissions AS p ON u.id = p.user_id
WHERE u.is_active = 0;

הסבר: מחברים חשבונות להרשאות ומסננים חשבונות לא פעילים. גם רשומה שכל דגליה אפס נכללת בביקורת זו.

תוצאה ובדיקה: חשבונות לא פעילים עם רשומות הרשאה שנותרו.

ה2. מצאו קבצים המשותפים ליותר משני משתמשים.

רמז

קבצו לפי קובץ

חשיפת פתרון והסבר
SELECT f.id, f.original_name, COUNT(DISTINCT p.user_id) AS shared_count
FROM files AS f JOIN file_permissions AS p ON f.id = p.file_id
WHERE p.user_id <> f.owner_id AND (p.can_view = 1 OR p.can_download = 1 OR p.can_edit = 1 OR p.can_delete = 1)
GROUP BY f.id, f.original_name
HAVING COUNT(DISTINCT p.user_id) > 2;

הסבר: WHERE מסנן שיתופים תקפים מבחינת הדגלים, GROUP BY מקבץ לפי קובץ ו-HAVING מסנן קבוצות לאחר הספירה. לא סופרים בעלים.

תוצאה ובדיקה: קבצים עם לפחות שלושה מקבלי שיתוף שונים; לא בהכרח חשבונות פעילים.

ה3. הציגו את כל ההרשאות המאפשרות מחיקה.

רמז

סננו can_delete

חשיפת פתרון והסבר
SELECT p.id, f.original_name, u.username, p.can_delete
FROM file_permissions AS p JOIN files AS f ON p.file_id = f.id
JOIN users AS u ON p.user_id = u.id
WHERE p.can_delete = 1;

הסבר: מסננים את דגל המחיקה ומציגים הקשר קריא לביקורת.

תוצאה ובדיקה: כל רשומות הרשאת המחיקה, גם של חשבון לא פעיל.

ה4. הציעו מדיניות לצמצום הרשאות מיותרות והסבירו איך השרת יאכוף אותה.

רמז

חשבו על הרשאה מזערית

חשיפת פתרון והסבר

הסבר: מדיניות הרשאה מזערית: ברירת מחדל היא דחייה. השרת מאמת Session, בודק חשבון פעיל, מזהה את הקובץ ובודק בעלות או את דגל הפעולה המתאים. רק בעלים מורשה לשתף ולבטל שיתוף לפי המדיניות המוצעת. משתמשים לא פעילים נחסמים גם אם נשארה הרשאה. יש להשתמש בשאילתות פרמטריות, לתעד אירועים ולבדוק הרשאה בכל בקשה.

תוצאה ובדיקה: בדיקות: משתמש ללא הרשאה נדחה; צפייה אינה מאפשרת הורדה; חשבון לא פעיל נדחה; ביטול שיתוף נכנס לתוקף בבקשה הבאה.

שאלות הבנה וחשיבה

1. מה הסיכון ב־UPDATE ללא WHERE?

רמזעדכון כל הרשומות בטבלה
תשובה והסבר

ללא WHERE כל שורות הטבלה מתעדכנות. לדוגמה UPDATE users SET is_active = 0 ישבית את כולם. לפני עדכון יש להריץ SELECT עם אותו תנאי ולבדוק מספר רשומות מושפעות.

2. מה תפקיד FOREIGN KEY?

רמזשמירה על קשר תקין בין רשומות
תשובה והסבר

מפתח זר מבטיח שהערך מפנה לרשומה קיימת בטבלת היעד. למשל files.owner_id מפנה ל-users.id. ב-SQLite יש להפעיל PRAGMA foreign_keys = ON בכל חיבור.

3. האם הרשאת can_view=1 מספיקה להורדת קובץ?

רמזלא, נדרשת can_download או בעלות
תשובה והסבר

לא. נדרשת הרשאת can_download = 1 או בעלות לפי מדיניות המערכת, וגם חשבון פעיל וזהות מאומתת.

4. מדוע אין להסתמך על user_id שהלקוח שולח?

רמזכי הלקוח יכול לזייף זהות; השרת מאמת משתמש והרשאות
תשובה והסבר

הלקוח יכול לשנות user_id בבקשה ולהתחזות למשתמש אחר. השרת צריך להפיק את הזהות מתוך Session מאומת ולבדוק הרשאה לפעולה ולקובץ.

סיכום ורפלקציה

דוגמה לרפלקציה (לא תשובה אישית מחייבת)

למדתי שבעלות והרשאת שיתוף הן קשרים שונים. התקשיתי בחיבור טבלת המשתמשים פעמיים, ופתרתי זאת באמצעות כינויים נפרדים לבעלים ולמקבל ההרשאה. הבנתי שצריך לבדוק הרשאות בשרת ולא רק בממשק.

הערות למורה: לדוגמה, נותר לבדוק כיצד ביטול הרשאה משפיע על בקשה חדשה. יש לכתוב קושי אמיתי מהעבודה.
