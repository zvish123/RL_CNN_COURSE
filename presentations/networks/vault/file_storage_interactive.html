איפה שומרים קובץ בכספת דיגיטלית?

שתי ארכיטקטורות לאחסון קבצים, דוגמאות קוד, הצפנת AES-GCM ואתגרי תכנון.

מטרת השיעור: לבחור שיטת אחסון מתאימה, להבין מה נשמר ב־DB, ולהגן על תוכן הקובץ.

1. מה בעצם צריך לשמור?

המשתמש מעלה קובץ report.pdf. השרת צריך לשמור גם את התוכן הבינארי וגם את המידע המתאר אותו (Metadata).

📄 תוכן הקובץ

רצף בתים (bytes) שמרכיב את ה־PDF, התמונה או קובץ ה־ZIP.

b'%PDF-1.7\n...'

🗃️ מידע על הקובץ

מזהה, שם להצגה, בעלים, גודל, תאריך, תיקייה לוגית והרשאות.

id = 17 owner_id = 3 original_name = 'report.pdf' size_bytes = 48201
בשתי השיטות הטבלאות users, files, file_permissions משמשות לניהול משתמשים והרשאות. ההבדל: איפה נשמרים הבתים של הקובץ?

2. שיטה א׳ — הקובץ בדיסק השרת

השרת שומר את תוכן הקובץ בתיקייה פיזית. בטבלת files נשמר storage_path המצביע לקובץ.

יתרונות

✓ נוח לקבצים גדולים ולקריאה/כתיבה במקטעים.
✓ בסיס הנתונים קטן יותר.
✓ אפשר לנהל את הקבצים בנפרד.

חסרונות

✕ צריך לגבות גם DB וגם דיסק.
✕ צריך לתאם בין שתי מערכות אחסון.
✕ קובץ עלול להישאר בדיסק בלי רשומה, או להפך.

חשוב: הלקוח לא בוחר נתיב שרירותי בשרת. השרת יוצר שם אחסון בטוח ובודק הרשאות לפני גישה.

3. שיטה א׳ — דוגמת קוד: שמירה והורדה

דוגמה בסיסית לקובץ קטן. בפרויקט אמיתי יש להוסיף אימות משתמש, הגבלת גודל, טיפול בשגיאות ותיאום כשלי דיסק/DB.

from pathlib import Path from uuid import uuid4 STORAGE_ROOT = Path('server_storage') def save_on_disk(session, owner_id, name, data): folder = STORAGE_ROOT / f'user_{owner_id}' folder.mkdir(parents=True, exist_ok=True) path = folder / f'{uuid4().hex}.bin' path.write_bytes(data) # bytes -> disk record = VaultFile( owner_id=owner_id, original_name=name, storage_path=str(path), size_bytes=len(data) ) try: session.add(record) session.commit() except Exception: session.rollback() path.unlink(missing_ok=True) raise return record.id
from pathlib import Path def load_from_disk(session, file_id, current_user): record = session.get(VaultFile, file_id) if record is None: raise FileNotFoundError() # Must also check file_permissions! require_download_permission(session, current_user, record) return Path(record.storage_path).read_bytes() # For large files: stream in chunks instead # of read_bytes() / write_bytes().
from sqlalchemy import Integer, String, ForeignKey from sqlalchemy.orm import Mapped, mapped_column class VaultFile(Base): __tablename__ = 'files' id: Mapped[int] = mapped_column(primary_key=True) owner_id: Mapped[int] = mapped_column(ForeignKey('users.id')) original_name: Mapped[str] = mapped_column(String(255)) storage_path: Mapped[str] = mapped_column(String(500), unique=True) size_bytes: Mapped[int] = mapped_column(Integer)
שימו לב: write_bytes ו־read_bytes עובדים עם בתים. הם אינם מצפינים את הקובץ.

4. שיטה ב׳ — הקובץ בתוך SQLite

SQLite יכול לשמור את תוכן הקובץ בשדה BLOB. ב־SQLAlchemy משתמשים ב־LargeBinary.

יתרונות

✓ תוכן הקובץ והרשומה נשמרים באותה טרנזקציה.
✓ גיבוי לוגי פשוט יותר — בסיס נתונים אחד.
✓ נוח לפרויקט קטן עם קבצים קטנים.

חסרונות

✕ בסיס הנתונים גדל במהירות.
✕ עבודה עם ORM רגיל עלולה לטעון BLOB גדול לזיכרון.
✕ כתיבות גדולות עשויות לעכב כתיבות אחרות.

SQLite מאפשר קוראים רבים, אך רק כותב אחד בכל רגע. מצב WAL אינו משנה את מגבלת הכותב היחיד.

5. שיטה ב׳ — דוגמת קוד: BLOB

from sqlalchemy import Integer, String, LargeBinary, ForeignKey from sqlalchemy.orm import Mapped, mapped_column class VaultFile(Base): __tablename__ = 'files' id: Mapped[int] = mapped_column(primary_key=True) owner_id: Mapped[int] = mapped_column(ForeignKey('users.id')) original_name: Mapped[str] = mapped_column(String(255)) folder_path: Mapped[str] = mapped_column(String(500), default='/') content: Mapped[bytes] = mapped_column(LargeBinary, nullable=False) size_bytes: Mapped[int] = mapped_column(Integer)
def save_as_blob(session, owner_id, name, data): record = VaultFile( owner_id=owner_id, original_name=name, folder_path='/לימודים/', content=data, # actual file bytes size_bytes=len(data) ) session.add(record) session.commit() return record.id # Example: data = Path('report.pdf').read_bytes()
def download_blob(session, file_id, current_user): record = session.get(VaultFile, file_id) if record is None: raise FileNotFoundError() require_download_permission(session, current_user, record) return record.content # bytes sent to client # Client: Path('download.pdf').write_bytes(data)
ההבדל המרכזי: בשיטה א׳ נשמר storage_path; בשיטה ב׳ נשמר content מסוג LargeBinary. בשתי השיטות הרשאות נבדקות בשרת.

שאלת יישום

מערכת מאפשרת העלאת סרטונים של 2GB על ידי משתמשים רבים. האם נכון להשתמש ב־f.read() ולהכניס את התוצאה ישירות ל־ORM? הסבירו מדוע.

8. למה בכלל להצפין קבצים?

ללא הצפנה

📄 PDF גלוי←💾 דיסק / BLOB

מי שמשיג גישה לא מורשית לתוכן המאוחסן עלול לקרוא אותו.

עם הצפנה

📄 PDF←🔐 AES-GCM←🔣 Ciphertext

התוכן המאוחסן אינו קריא ללא מפתח מתאים. AES-GCM גם מזהה שינוי לא מורשה בתוכן.

חשוב: הצפנה אינה מחליפה בדיקות הרשאות. TLS מגן על המידע בתעבורה; הצפנת קבצים מגינה על המידע במנוחה. גם מפתחות ההצפנה חייבים הגנה.
אם התקשורת משתמשת ב־TLS, האם אפשר לוותר על הצפנת הקבצים המאוחסנים?

9. AES-GCM — איך מתבצעת ההצפנה?

אלגוריתם הצפנה סימטרי מאומת: אותו מפתח משמש להצפנה ולפענוח, וניתן לזהות שינוי בנתונים.

Key — מפתח

סוד בן 128/192/256 ביט. בדוגמה נשתמש במפתח 256 ביט.

Nonce — ערך חד־פעמי

בדוגמה: 12 בתים אקראיים. אסור לחזור על אותו Nonce עם אותו מפתח.

אם המפתח נחשף, ההצפנה לא תגן על הקבצים. יש לנהל מפתחות בנפרד מתוכן ה־DB ומגיבויים נגישים.

10. קוד עובד: הצפנה ופענוח

התקנה: pip install cryptography

import os from cryptography.hazmat.primitives.ciphers.aead import AESGCM # Demo only: generate once and store securely! key = AESGCM.generate_key(bit_length=256) aes = AESGCM(key) nonce = os.urandom(12) plaintext = b'Secret project file' ciphertext = aes.encrypt(nonce, plaintext, None) # ciphertext includes authentication tag print('Encrypted bytes:', ciphertext)
from cryptography.exceptions import InvalidTag try: recovered = AESGCM(key).decrypt( nonce, ciphertext, None ) assert recovered == plaintext print('Successfully decrypted') except InvalidTag: print('Wrong key, nonce, or modified data') # Never reuse (key, nonce) for another encryption!
