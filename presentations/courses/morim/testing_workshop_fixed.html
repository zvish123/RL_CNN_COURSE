שלב 1 · פתיחה: האם אתם סומכים על הקוד? (5 דקות)

מערכת הרשמה לסדנאות מחזירה מחיר לפי גיל. אלה הדרישות:

גיל מחיר
מתחת ל־0 שגיאה
0–12 20 ₪
13–17 30 ₪
18–64 50 ₪
65 ומעלה 25 ₪

הגיל חייב להיות מספר שלם. קלט מסוג אחר אינו תקין.

def ticket_price(age):
    if age < 0:
        raise ValueError("Invalid age")
    if age <= 12:
        return 20
    if age <= 18:
        return 30
    if age < 65:
        return 50
    return 25

הקוד נוצר ב-AI. ארבע בדיקות רגילות עברו: גילאים 8, 15, 30 ו-70.

דיון קצר: מה למדנו בשלב זה?

האם הצלחה של מספר בדיקות מוכיחה נכונות? מה ההבדל בין ״הקוד רץ״ ל״הקוד עומד בדרישות״?

שלב 2 · ציד באגים באמצעות בדיקות (10 דקות)

בלי לתקן את הקוד, בחרו לפחות חמישה מקרי בדיקה. ציינו קלט, תוצאה צפויה לפי הדרישות וסיבה לבחירה. אפשר להוסיף שורות.

הצג / הסתר את הקוד המקורי

הקוד שנוצר באמצעות AI:

def ticket_price(age):
    if age < 0:
        raise ValueError("Invalid age")
    if age <= 12:
        return 20
    if age <= 18:
        return 30
    if age < 65:
        return 50
    return 25
קלט תוצאה צפויה למה דווקא זה?

תוצאות חשובות: גיל 18 אמור להחזיר 50 אך מחזיר 30; גיל 15.5 אמור להידחות אך מחזיר 30. בדיקות גיל 12, 13, 17, 64 ו-65 מדגימות ערכי גבול.

שימו לב: בקוד הנוכחי גם מחרוזת עשויה להוביל ל-TypeError עקב השוואה למספר, אך אין בדיקת סוג מפורשת. בקלט מסוג float שאינו שלם יש כשל ממשי.

דיון קצר: מה למדנו בשלב זה?

מה תרמו ערכי הגבול? כיצד יודעים מהי התוצאה הצפויה, בלי להעתיק אותה מהקוד?

שלב 4 · מתקנים את הקוד ומוכיחים שהתיקון עובד (15 דקות)

כעת עוברים מאיתור שגיאות לתיקון מבוסס דרישות. כתבו מימוש מתוקן של ticket_price(age) ובדיקות שיוכיחו שהוא מתמודד עם מקרים רגילים, ערכי גבול וקלטים לא תקינים.

הבחנה חשובה: בדרישות המקוריות כתוב ״65 ומעלה״, ולכן גם גיל 121 אמור לקבל מחיר 25 ₪. עם זאת, במערכת אמיתית ראוי לברר האם גיל מעל 120 נחשב קלט לא סביר.
אל תוסיפו מגבלה בלי להגדיר אותה כדרישה חדשה ולהבהיר את השינוי.

רשימת בדיקה עצמית: ודאו שהתייחסתם לגילאים 0, 12, 13, 17, 18, 64, 65, 120, 121, לגיל שלילי, ל-15.5, למחרוזת, ל-None ול-True. האם סוג השגיאה המוחזרת עקבי?

הצגת פתרון אפשרי למנחה – לאחר ניסיון עצמאי 
def ticket_price(age):
    if type(age) is not int:
        raise TypeError("Age must be an integer")
    if age < 0:
        raise ValueError("Age must be non-negative")
    if age <= 12:
        return 20
    if age <= 17:
        return 30
    if age <= 64:
        return 50
    return 25

הפתרון עומד בדרישות המקוריות, כולל גיל 121. אם מגדירים דרישה חדשה שגיל מעל 120 אינו תקין, יש להוסיף בדיקת age > 120 ולהעלות ValueError, ולעדכן גם את הבדיקות והאפיון. שימוש ב-type(age) is not int מונע קבלה של True כגיל 1.

דיון קצר: מה למדנו בשלב זה?

מדוע תיקון הבאג בגיל 18 אינו מספיק? מה ההבדל בין דרישה מפורשת, הנחה סבירה ושינוי באפיון? כיצד בדיקות רגרסיה מגינות מפני תקלות חדשות?

שלב 5 · מי בודק את הבדיקות? (10 דקות)

ב-Mutation Testing משנים בכוונה פרט בקוד ובודקים האם חבילת הבדיקות מגלה את השינוי. כאן שלוש מוטציות אפשריות. סמנו אילו בדיקות שלכם יגלו כל אחת.

מוטציה שינוי בקוד איזו בדיקה תיכשל?
א׳ age <= 18 במקום age <= 17
ב׳ age <= 65 במקום age < 65
ג׳ return 25 במקום return 20 בקבוצת הילדים

הניחו שבכל פעם בודקים מוטציה אחת מול מימוש בסיס תקין. אחרת הבאג המקורי בגיל 18 עלול לבלבל את הפרשנות.

פתיחת רמז למנחה

א׳: גיל 18; ב׳: גיל 65; ג׳: גיל 8 או 12. בדיקה שמגלה שינוי התנהגותי מחזקת את האמון בחבילת הבדיקות, אך אינה מוכיחה שלמות.

דיון קצר: מה למדנו בשלב זה?

האם 100% בדיקות שעוברות פירושם 100% נכונות? כיצד אפשר להעריך את איכות הבדיקות עצמן?
