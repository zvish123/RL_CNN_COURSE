סיפור המערכת

במערכת כספת קבצים, משתמש רשום יכול להתחבר, להעלות קובץ, לשתף קובץ עם משתמש אחר ולהוריד קובץ שיש לו הרשאה אליו. מנהל יכול לצפות באירועים חשודים. השרת מאמת הרשאות ושומר מטא־דאטה במסד נתונים.

Use Case Diagram — מה המערכת עושה?

מטרה

להציג שחקנים (Actors) ואת מטרותיהם מול המערכת, בלי להתחייב למימוש.

שחקן יכול להיות אדם או מערכת חיצונית.

סימונים

דמות = Actor; אליפסה = Use Case; מלבן = גבול מערכת; קו = קשר השתתפות.

<<include>> — התנהגות נדרשת ומשותפת; <<extend>> — הרחבה מותנית/אופציונלית בנקודת הרחבה.

לא מייצגים ב־Use Case פונקציות פנימיות כמו save_to_db() רק משום שהן קיימות בקוד.

תרשים Use Case של הכספת — כולל התראה

החלטת מידול: ״קבלת התראה על אירוע חריג״ היא יכולת שהמשתמש חווה, ולכן אפשר להציגה כ־Use Case. המערכת יוזמת את ההתראה כאשר מתגלה אירוע; אין לפרש את קו הקשר כאילו המשתמש יוזם אותה. זיהוי האירוע עצמו הוא התנהגות פנימית או תרחיש נפרד לפי גבול המערכת.

איזה פריט אינו Use Case מתאים?

«include» — התנהגות נכללת

במערכת הכספת, הורדת קובץ כוללת בדיקת הרשאות. אם בחרנו להציג את בדיקת ההרשאות כתרחיש שימוש משותף, החץ מצביע מהורדת קובץ אל בדיקת הרשאות.

כלל: התרחיש הראשי משלב את ההתנהגות הנכללת בכל הפעלה. בדיקת הרשאות אינה חייבת להיות Use Case עצמאי אם היא רק פרט מימוש פנימי.

מהו כיוון החץ של include?

«extend» — הרחבה מותנית

כאשר ניסיון הורדת קובץ מזוהה כחריג, המערכת עשויה ליצור התראת אבטחה. התראה אינה חלק מכל הורדה, ולכן ניתן למדל אותה כהרחבה מותנית.

תנאי הרחבה לדוגמה: [זוהה ניסיון גישה חריג]. החץ יוצא מהתרחיש המרחיב ומצביע לתרחיש הראשי. ב־UML אפשר לציין גם extension point מפורש.

משימת יישום

הוסיפו לתרשים הכספת תרחיש ״הוספת חבר לקבוצה״. החליטו האם ״בדיקת הרשאת מנהל קבוצה״ תוצג כ־include או כפרט מימוש, ונמקו. תכננו גם הרחבה מותנית להתראה על ניסיון צירוף בלתי מורשה.

בדיקת הרשאת מנהל קבוצה היא חובה, אך אינה בהכרח Use Case עצמאי: יש לשקול אם מדובר בהתנהגות משותפת ומשמעותית. התראה על ניסיון חריג יכולה להיות «extend» בתנאי מוגדר. הימנעו מהפיכת כל פונקציה פנימית לאליפסה.

איך בונים Use Case נכון?

1. מגדירים גבול מערכת.

2. מזהים Actors חיצוניים.

3. כותבים מטרות משתמש בניסוח פועל + מושא.

4. מחברים שחקנים למטרות.

5. מוסיפים include/extend רק כשיש הצדקה סמנטית.

החלטת תכנון חשובה

האם ״בדיקת הרשאה״ חייבת להופיע כ־Use Case?

בדרך כלל לא כאליפסה עצמאית: זו פעולה פנימית במימוש התרחיש. אם ממדלים התנהגות משותפת משמעותית למספר מקרי שימוש, אפשר לשקול include — לא כל פונקציה היא Use Case.
מתי משתמשים ב־<<extend>>?

מתרשים לתרחיש מפורט

Use Case: שיתוף קובץ

שחקן ראשי: משתמש מחובר | תנאי מקדים: המשתמש בעל הרשאת שיתוף לקובץ.

מסלול הצלחה: 1. המשתמש בוחר קובץ ונמען. 2. המערכת בודקת שהקובץ קיים ושהמשתמש רשאי לשתף אותו. 3. המערכת מוודאת שהנמען קיים. 4. הרשאת גישה נשמרת. 5. המשתמש מקבל אישור.

מסלול חלופי: אין הרשאה → אין שינוי במסד הנתונים → הודעת שגיאה.

תנאי סיום: נוצרה הרשאה חדשה או שהפעולה נדחתה ללא שינוי.

תרשים Use Case מציג את המטרות; תיאור טקסטואלי של Use Case מפרט את הצעדים והחריגים. הם משלימים זה את זה.

למה לא מחלקה אחת ענקית?

הפרדת אחריות משפרת בדיקות, תחזוקה ושינוי מסד נתונים ללא שינוי הלוגיקה העסקית. לא חייבים מחלקה לכל שם עצם; בוחרים לפי אחריות, מצב וקשרים.

מי צריך להחליט האם המשתמש רשאי לשתף קובץ?

מתי נכון להשתמש בתבנית עיצוב?

לא בוחרים Pattern רק כדי להציג UML מרשים. מזהים קודם בעיה חוזרת, שינוי צפוי או צימוד לא רצוי.

Repository + Service

הפרדה בין לוגיקה עסקית (FileService) לבין גישה למסד (FileRepository). זו בחירה ארכיטקטונית שימושית; לא חייבים להציג אותה כ־GoF Pattern.

Strategy — מומלץ להרחבת הרשאות

אם צפויות מדיניות הרשאה מתחלפות: PermissionPolicy כממשק, ומימושים כגון UnionPolicy או StrictPolicy. PermissionService מפעיל מדיניות ללא תלות במימושה.

Observer — להתראות

אם מספר רכיבים צריכים להגיב לאירוע חריג (UI, דוא״ל, יומן אירועים), מנגנון פרסום–מנוי יכול למנוע צימוד ישיר. כאשר יש ערוץ התראה אחד בלבד, פתרון פשוט עשוי להיות עדיף.

Factory — רק כשצריך

מתאים אם יוצרים כמה סוגי אובייקטים לפי הגדרות/סוגי אחסון. אין צורך ב־Factory כדי ליצור כל FileRecord.

נוספו EmailNotifier ו־DashboardNotifier לאירועים חריגים. מה כדאי לשקול?

אתגר: הציגו Class Diagram של PermissionService → PermissionPolicy (תלות) ושל שתי מחלקות שמממשות את הממשק (Realization). נמקו האם המורכבות מוצדקת.

כללי UML: Sequence Diagram

מטרת התרשים: להציג אינטראקציה אחת בזמן בין משתתפים; הזמן מתקדם מלמעלה למטה.

מיפוי המושגים אל התרשים

Participant / Lifeline: ארבע הכותרות וקווי החיים האנכיים שמתחתיהן. Message: החצים הכחולים עם שם פעולה ופרמטרים. Return: החצים הירוקים המקווקווים וערכי החזרה. Activation: הפסים הכחולים הצרים על קווי החיים. alt: המסגרת הכתומה עם מסלול מורשה ומסלול דחייה. loop: המסגרת הסגולה המציינת חזרה על העברת מקטעים.

התרשים סכמטי לצורכי לימוד. בדוגמה, ההרשאה נבדקת לפני קריאת תוכן הקובץ; מסלול הדחייה אינו קורא לאחסון.

אלמנטים נוספים: opt ו־par

opt [condition] — מסגרת עם ענף יחיד, לדוגמה: [notify_user] לשליחת הודעה אופציונלית.

par — מסגרת עם שני אזורים או יותר המייצגים פעולות שיכולות להתבצע במקביל, למשל כתיבה ליומן ושליחת התראה.

אלמנטים נוספים: create ו־destroy

create: חץ יצירה המצביע לראש קו החיים של אובייקט חדש, שמתחיל בנקודת היצירה.

destroy: סימן X בסיום קו החיים של אובייקט שהושמד. אין לסמן X בכל החזרת ערך מפונקציה.

נבחר ענף [else] של alt: השרת מחזיר AccessDenied, לא מפעיל את FileStorage.read ולא מעביר bytes למשתמש.

במימוש מלא נוסיף גם מחלקת User, שכבת תקשורת ClientHandler, אימות זהות ומדיניות הרשאות. השמטנו אותן כאן כדי להמחיש אחריות אחת היטב. את הבדיקה האמיתית יש לבצע בשרת ולא להסתמך על ממשק המשתמש.

Sequence Diagram — איך התרחיש מתרחש?

מטרה

לתאר סדר הודעות/קריאות בין שחקן לאובייקטים לאורך הזמן. הזמן מתקדם מלמעלה למטה.

סימונים

Lifeline — קו חיים אנכי מקווקו; Message — חץ קריאה; Return — חץ חזרה מקווקו; Activation — פס ביצוע; alt — מסלולים מותנים; loop — חזרה.

Sequence אינו תרשים זרימת נתונים (DFD): הוא מציג אינטראקציות בזמן, ובתוויות ההודעות ניתן לציין פרמטרים, ערכי החזרה והמידע שעובר.

Sequence: שיתוף קובץ

זהו תרשים לימודי מפושט של מסלול ההצלחה. ביישום אמיתי יש להציג גם alt למקרה של הרשאה חסרה, קובץ חסר או נמען לא קיים, ולמקם את בדיקת ההרשאה לפני כתיבת השיתוף.

איך מציגים תנאים וזרימת נתונים?

פרמטרים נכתבים על חץ הקריאה; ערך מוחזר על חץ החזרה.

קטע alt

alt [file missing]
    return NOT_FOUND
else [no permission]
    return FORBIDDEN
else [recipient missing]
    return UNKNOWN_USER
else [all checks pass]
    grant_access(...)
    return SUCCESS

התנאים בסוגריים מרובעים הם guards. אין לכתוב למסד לפני שהבדיקות הושלמו.

אתגר יישום: הורדת קובץ

משתמש מבקש להוריד קובץ משותף. השרת צריך לוודא שהקובץ קיים ושהמשתמש מורשה לגשת אליו, ואז להעביר את תוכנו.

משימה קבוצתית — 6 דקות

  1. הגדירו Actor ו־Use Case.
  2. בחרו שלוש מחלקות מרכזיות ואחריות לכל אחת.
  3. כתבו רצף של לפחות חמש הודעות, כולל תרחיש שגיאה.

Use Case: משתמש — הורדת קובץ.

מחלקות: ClientHandler (תקשורת), FileService (הרשאות ותיאום), FileRepository (מטא־דאטה); בנוסף FileStorage (קריאת תוכן הקובץ).

Sequence: בקשה → get_file → בדיקת הרשאת גישה → alt: כישלון מחזיר שגיאה; הצלחה → קריאת תוכן מ־FileStorage → שליחת bytes ללקוח.

חשוב: אין לשלוח תוכן קובץ לפני בדיקת ההרשאה.

מצאו את שגיאת התכנון

תכנון א׳

ב־Use Case מופיעות האליפסות: open_socket(), SELECT * FROM files, ״שיתוף קובץ״.

ערבוב מטרות משתמש עם פעולות מימוש. השאירו ״שיתוף קובץ״ כ־Use Case והעבירו פרטי SQL/Socket לתכנון המימוש.

תכנון ב׳

הלקוח בודק הרשאות מקומית ושולח לשרת authorized=True; השרת שומר שיתוף ללא בדיקה.

השרת סומך על נתון מהלקוח. יש לאמת זהות והרשאות בצד השרת באמצעות מקור נתונים מהימן.

תכנון ג׳

ב־Sequence מופיעה קריאה ל־grant_access() לפני בדיקת ההרשאות.

סדר פעולות שגוי; בדיקות קיום והרשאה חייבות להקדים שינוי מצב. תרשים הרצף מסייע לגלות באגים תכנוניים לפני כתיבת קוד.

2. איזה תרשים מציג multiplicity כגון 1..*?
3. איך מציגים פרמטרים שעוברים בין אובייקטים?
4. מה נכון כאשר Sequence חושף צורך במחלקה חדשה?

אתגר תכנון: קבוצות והרשאות בכספת

דרישת לקוח חדשה

משתמש מורשה יכול לפתוח קבוצה, לצרף משתמשים לקבוצה ולנהל גישה לקבצים בשתי רמות: הרשאה ישירה למשתמש והרשאה לקבוצה. חברי קבוצה נהנים מההרשאות שהוקצו לקבוצה.

שלב א׳ — Use Case: הוסיפו לתרשים את מקרי השימוש: יצירת קבוצה, צירוף משתמש לקבוצה, הסרת חבר מקבוצה, הקצאת הרשאת קובץ למשתמש, הקצאת הרשאת קובץ לקבוצה וביטול הרשאה. הגדירו מי רשאי לבצע כל פעולה.

שלב ב׳ — Class: הרחיבו את המחלקות והקשרים. שקלו User, Group, GroupMembership, File, FilePermission, PermissionService. ציינו multiplicity ואחריות של כל מחלקה.

שלב ג׳ — Sequence: בנו רצף ל״הורדת קובץ על סמך הרשאת קבוצה״, עם בדיקת חברות, בדיקת הרשאה, alt למורשה/לא מורשה והחזרת bytes רק לאחר אישור.

מה נכון לגבי משתמש שנמצא בשתי קבוצות?

בחרו מדיניות הרשאות והגנו עליה

שאלות שעליכם להכריע

  1. מי רשאי לצרף ולהסיר חברים — יוצר הקבוצה, מנהל הקבוצה או מנהל מערכת?
  2. מהן ההרשאות: צפייה, הורדה, העלאה, עריכה, שיתוף?
  3. אם למשתמש יש הרשאה ישירה וגם קבוצתית, כיצד מחשבים הרשאה אפקטיבית?
  4. מה קורה כאשר משתמש מוסר מקבוצה? האם הגישה לקובץ מתבטלת מייד?
  5. כיצד מונעים מלקוח לזייף group_id או authorized=True?

תוצר להגשה

1. Use Case מעודכן עם Actors והרשאות פעולה.

2. Class Diagram עם קשרי User–Group ו־File–Permission.

3. שני Sequence Diagrams: צירוף חבר לקבוצה; הורדת קובץ באמצעות הרשאת קבוצה, כולל כישלון.

4. טבלת בדיקות: גישה ישירה, גישה דרך קבוצה, היעדר הרשאה, הסרה מקבוצה, ניסיון שינוי לא מורשה.

מידול אפשרי: GroupMembership מקשרת User ו־Group; FilePermission מחזיקה file_id, principal_type, principal_id, permission. לחלופין אפשר להגדיר UserPermission ו־GroupPermission בנפרד. אין פתרון יחיד.

מדיניות בסיסית מומלצת לתרגיל: איחוד הרשאות חיוביות (ללא deny מפורש), הרשאה ישירה או הרשאה דרך כל קבוצה שבה המשתמש חבר; ברירת מחדל היא דחייה. כל בדיקה מתבצעת בשרת מול נתונים מהימנים. יש להגדיר במפורש מה קורה בהרשאות סותרות אם מוסיפים deny.

רצף הורדה: Client → Handler → PermissionService → MembershipRepository / PermissionRepository → alt [מורשה] FileStorage.read() → bytes; [לא מורשה] שגיאה ללא תוכן.
