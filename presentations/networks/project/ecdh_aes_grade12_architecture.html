03 | TLS

אז למה לא להסתפק ב־TLS?

TLS 1.3 כבר משתמש בדרך כלל בהחלפת מפתחות זמנית, למשל X25519, ומספק Forward Secrecy לתעבורה.

אם המטרה היא רק להצפין תקשורת לקוח–שרת, TLS תקין ומאומת הוא בדרך כלל הפתרון הנכון והמספיק.

הצפנת Payload יכולה להועיל כאשר המידע עובר דרך רכיבי ביניים שמסיימים TLS, או כאשר יש צורך לשמור תוכן מוצפן בנפרד. היא אינה מחליפה TLS.

04 | ECDH

מה זה X25519?

כל צד יוצר זוג מפתחות זמני: פרטי וציבורי. מחליפים רק מפתחות ציבוריים; כל צד מחשב את אותו סוד משותף.

לקוח
private A
public A
⇄
שרת
private B
public B
X25519 הוא מנגנון הסכמה על סוד, לא אלגוריתם הצפנת הודעות ולא מנגנון אימות זהות.

06 | אימות זהות

אם התוקף יכול להחליף את המפתחות הציבוריים, הוא יכול לנהל הסכמה נפרדת עם כל צד ולקרוא הודעות.

⇄

לכן יש לאמת את זהות השרת, למשל באמצעות TLS עם אימות תעודה, או חתימות על מפתחות ההחלפה במסגרת פרוטוקול מתוכנן היטב.
07 | HKDF

הסוד המשותף אינו מפתח AES ישיר

X25519
Shared Secret
←
HKDF-SHA256
salt + info
←
AES Key
32 bytes

HKDF גוזר מפתח מתאים מתוך הסוד המשותף, עם הפרדה בין מטרות שימוש שונות. רצוי להפריד מפתחות לשני כיווני התקשורת.

אין להשתמש במפתח פרטי או בסוד המשותף ישירות כמפתח AES ללא תהליך גזירה מתאים.
08 | AES-GCM

הצפנה + אימות שלמות

AES-GCM הוא מצב הצפנה מאומתת (AEAD). הוא מחזיר Ciphertext ותג אימות שמאפשר לזהות שינוי במידע.

Plaintext
+ Key + Nonce
←
AES-GCM
←
Ciphertext
+ Tag
אסור לעשות שימוש חוזר באותו Nonce עם אותו מפתח AES-GCM. יש לתכנן מנגנון ייחודיות, במיוחד בתקשורת דו־כיוונית.
09 | הדמיית Payload

איך נראית הצפנה?

בחרו פעולה

התוצאה היא המחשה ויזואלית בלבד, אינה AES אמיתי ואינה מיועדת לאבטחת מידע.

10 | Forward Secrecy

מה מרוויחים ממפתחות זמניים?

אם הסכמת המפתחות הזמנית מאומתת והמפתחות הפרטיים הזמניים נמחקים, פגיעה מאוחרת במפתח הזהות הקבוע אינה מספיקה כשלעצמה לפענוח תעבורת עבר מוקלטת.

TLS 1.3 עם החלפת מפתחות זמנית כבר מספק בדרך כלל תכונה זו.

Forward Secrecy אינה מגינה מפני גניבת מפתח Session בזמן שהוא פעיל, מפני פגיעה בנקודת קצה, או מפני עותק גלוי של קובץ שכבר נשמר.

11 | קוד Python

הסכמה וגזירת מפתח

from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

client_private = X25519PrivateKey.generate()
server_private = X25519PrivateKey.generate()

client_shared = client_private.exchange(server_private.public_key())
server_shared = server_private.exchange(client_private.public_key())
assert client_shared == server_shared

key = HKDF(
    algorithm=hashes.SHA256(),
    length=32,
    salt=None,
    info=b"grade12-demo-aes-gcm-v1"
).derive(client_shared)

דוגמה מקומית בלבד. במערכת אמיתית יש לבצע אימות מפתחות ולנהל תמליל handshake, salt והפרדת כיוונים.

12 | קוד Python

הצפנה ופענוח ב־AES-GCM

import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

aes = AESGCM(key)
nonce = os.urandom(12)  # יש להבטיח ייחודיות לכל מפתח
plaintext = "מידע רגיש".encode("utf-8")

ciphertext = aes.encrypt(nonce, plaintext, None)
restored = aes.decrypt(nonce, ciphertext, None)
assert restored == plaintext

מעבירים את ה־nonce יחד עם ה־ciphertext. הוא אינו סודי. המפתח חייב להישאר מוגן.

13 | אחסון

הצפנה בזמן העברה ≠ הצפנה בזמן אחסון

אם השרת מפענח קובץ ושומר אותו גלוי, הצפנת Payload לא מגינה על הקובץ המאוחסן.

הצפנה בצד השרת

מגינה מפני חשיפה מסוימת של דיסק/גיבוי. השרת יכול לפענח, ולכן פגיעה בשרת ובמפתחותיו מסוכנת.

הצפנה בצד הלקוח

עשויה למנוע מהשרת לראות תוכן, אם מפתחות הפענוח אינם מגיעים אליו. דורשת תכנון שיתוף, שחזור והרשאות.

16 | משימת סיום

תוצר נדרש מהתלמיד

הכינו תכנון אבטחה לפרויקט הכספת או לפרויקט לקוח–שרת אחר:

  1. הגדירו מי יכול לקרוא את המידע ומול איזה איום מגינים.
  2. הסבירו היכן TLS מספיק והיכן נדרשת הצפנת אחסון.
  3. בנו דמו X25519 → HKDF → AES-GCM.
  4. הציגו כיצד מאמתים את זהות הצד השני.
  5. כתבו בדיקות: פענוח תקין, שינוי Ciphertext, מפתח שגוי, Nonce ייחודי.
  6. תעדו היכן נשמרים המפתחות וכיצד מבטלים/מחליפים אותם.
מדד להצלחה: לא רק 'המידע מוצפן', אלא גם היכולת להסביר מי יכול לפענח, מתי, ובאילו תנאים.

מה בדיוק אנחנו רוצים להגן?

בתנועה (In Transit)

TLS מגן על המידע בזמן העברתו בין לקוח לשרת, כולל מפני האזנה ושינוי בדרך.

באחסון (At Rest)

AES-GCM מצפין את שדות המידע הרגישים בבסיס הנתונים. המפתח נשמר בנפרד.

בצד הלקוח

אפשר להצפין לפני השליחה, אך יש להחליט מי רשאי להחזיק במפתח ולפענח.

הצפנה נוספת מעל TLS אינה אוטומטית בטוחה יותר: יש להגדיר מודל איומים, זהות הצדדים, ניהול מפתחות וגבולות אמון.

שלוש ארכיטקטורות אפשריות

A · שרת יכול לפענח

Client → TLS → Server → AES-GCM → DB

פשוט, מתאים לרוב פרויקטי TCP/שרת.

B · הצפנה בצד הלקוח

Client (AES-GCM) → TLS → Server (Ciphertext) → DB

אם השרת לא אמור לפענח, המפתח חייב להישאר מחוץ להישג ידו.

C · העברת מפתח קיים

X25519 → HKDF → Wrapping Key → הצפנת DEK → Client

אפשרי, אך הלקוח יקבל מפתח שהשרת מכיר.

המלצה: A כברירת מחדל. C להעמקה קריפטוגרפית, עם DEK ייעודי למשתמש/קובץ ולא מפתח ראשי משותף.

חובה לאמת את החלפת המפתחות. X25519 לבדו אינו מונע MITM. מומלץ להשתמש ב־TLS מאומת ולשייך את ההחלפה לערוץ המאומת.

ה־DEK משמש להצפנת מידע רגיש; מפתח העטיפה הזמני משמש רק להעברת ה־DEK. אל תשתמשו באותו מפתח ראשי לכל המשתמשים.

קוד Python: X25519 ו־HKDF

from cryptography.hazmat.primitives.asymmetric.x25519 import X25519PrivateKey
from cryptography.hazmat.primitives.kdf.hkdf import HKDF
from cryptography.hazmat.primitives import hashes

client_sk = X25519PrivateKey.generate()
server_sk = X25519PrivateKey.generate()

# הדגמה מקומית בלבד: בפועל מעבירים רק מפתחות ציבוריים
client_secret = client_sk.exchange(server_sk.public_key())
server_secret = server_sk.exchange(client_sk.public_key())
assert client_secret == server_secret

# salt והקשר זהים בשני הצדדים, ואינם סודיים
salt = b"example-salt-32-bytes-change-me!"
def derive(secret):
    return HKDF(algorithm=hashes.SHA256(), length=32,
                salt=salt, info=b"grade12-dek-wrap-v1").derive(secret)

assert derive(client_secret) == derive(server_secret)
wrapping_key = derive(server_secret)
זהו קוד להמחשת המתמטיקה, לא פרוטוקול ייצור. בפועל: מפתחות ציבוריים מקודדים, salt אקראי, אימות זהות, הגנה מפני replay וקשירה ל־Session.

קוד Python: עטיפת מפתח DEK

import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

# בשרת: DEK ייעודי לקובץ/משתמש, לא מפתח מערכת ראשי
file_dek = AESGCM.generate_key(bit_length=256)
wrap_nonce = os.urandom(12)
context = b"file:42|key:v1"  # AAD חייב להיות זהה בפענוח
wrapped_dek = AESGCM(wrapping_key).encrypt(
    wrap_nonce, file_dek, context
)

# שולחים ללקוח: wrap_nonce, wrapped_dek, key_id
# בצד הלקוח, לאחר גזירת אותו wrapping_key:
received_dek = AESGCM(wrapping_key).decrypt(
    wrap_nonce, wrapped_dek, context
)
assert received_dek == file_dek
אם הלקוח נפרץ וה־DEK נחשף, המידע המוצפן באמצעותו עלול להיחשף. לעולם אל תשלחו את מפתח המערכת הראשי לכל לקוח.

קוד Python: הצפנה ושמירה ב־DB

import os
from cryptography.hazmat.primitives.ciphers.aead import AESGCM

# בלקוח, אחרי קבלת DEK ייעודי
plaintext = b"Sensitive grade-12 project data"
nonce = os.urandom(12)  # חדש לכל הצפנה באותו מפתח
aad = b"owner:7|file:42|v1"
ciphertext = AESGCM(received_dek).encrypt(nonce, plaintext, aad)

# השרת שומר: owner_id, file_id, key_id, nonce, ciphertext
record = {"owner_id": 7, "file_id": 42,
          "key_id": "file42-v1", "nonce": nonce,
          "ciphertext": ciphertext}

# בעת קריאה, הלקוח מפענח:
restored = AESGCM(received_dek).decrypt(
    record["nonce"], record["ciphertext"], aad)
assert restored == plaintext
AES-GCM כולל תג אימות בתוך ciphertext. ה־nonce אינו סודי אך חייב להיות ייחודי עבור אותו מפתח; AAD חייב להיבדק גם בעת הפענוח. יש לקשור בעלות והרשאות לנתונים בצד השרת.
