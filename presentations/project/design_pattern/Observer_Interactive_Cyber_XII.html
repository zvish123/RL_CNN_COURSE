Observer Pattern

איך גורמים למספר רכיבים להגיב לאירוע — בלי לקשור אותם זה לזה?

המשימה שלנו

נתכנן מערכת לניטור אירועי אבטחה, נזהה בעיית תכנון, נלמד את התבנית וניישם אותה בפייתון.

ניווט באמצעות הכפתורים למטה או מקשי החצים ← →. אפשר להציג במסך מלא באמצעות F11.

1. אירוע אחד — כמה תגובות

שרת כספת זיהה ניסיון התחברות חשוד. מה צריך לקרות?

📝 רישום ביומן האירועים
🔔 שליחת התרעה למנהל
📊 עדכון לוח הבקרה
שאלת פתיחה: האם מחלקת הניטור צריכה להכיר כל אחת מהמחלקות שמגיבות?

2. פתרון שעובד — אבל קשה להרחבה

class SecurityMonitor:
    def suspicious_login(self, username):

        self.logger.write(event)
        self.alerter.send(event)
        self.dashboard.refresh(event)

מה יקרה כשנוסיף SMS, דוא״ל או מערכת אנליטיקה?

המחלקה תלויה ישירות ברכיבים קונקרטיים. הוספת תגובה חדשה מחייבת שינוי בקוד שלה, ולכן קשה יותר לבדוק ולהרחיב אותה.

3. מה באמת משתנה?

נשאר קבוע

המערכת מזהה אירוע ומפיצה מידע עליו.

עשוי להשתנות

מספר המגיבים, זהותם, והפעולה שכל אחד מבצע.
עיקרון תכנון: נפריד בין מי שמייצר את האירוע לבין מי שמגיב אליו.

4. מהי Observer?

Observer היא תבנית התנהגותית (Behavioral) המגדירה קשר של אחד לרבים: כאשר Subject מפיץ עדכון, כל ה־Observers הרשומים מקבלים הודעה.

Subject / Publisher
מנהל רשימת מנויים ומפיץ אירועים
↓ notify(event)
Observer A
Observer B
Observer C

Observer אינה מחייבת סוקטים, תהליכונים או עבודה אסינכרונית. זוהי קודם כול דרך לארגן תלות בין אובייקטים.

5. ארבע פעולות שכדאי להכיר

attach(observer)

רישום Observer לקבלת עדכונים.

detach(observer)

הסרת Observer מרשימת המנויים.

notify(event)

הפצת האירוע למנויים הרשומים.

update(event)

התגובה של Observer לאירוע.
ה־Subject יודע שהמנוי מספק update, אבל אינו צריך לדעת אם הוא שולח הודעה, כותב לוג או מעדכן מסך.

הפעילו או הסירו מנויים ואז לחצו על הפצת אירוע.

8. ממשק משותף ל־Observers

from abc import ABC, abstractmethod

class Observer(ABC):
    @abstractmethod
    def update(self, event: str) -> None:
        pass

כל Observer קונקרטי יממש את update. כך ה־Subject יכול להפעיל את כולם באופן אחיד.

שאלה: האם ה־Subject צריך להכיר את המחלקה AlertObserver בשמה?
לא. הוא צריך רק לדעת שכל מנוי עומד בחוזה של update(event).

9. מימוש Subject

class SecurityMonitor:
    def __init__(self):
        self._observers = []

    def attach(self, observer: Observer):
        if observer not in self._observers:
            self._observers.append(observer)

    def detach(self, observer: Observer):
        if observer in self._observers:
            self._observers.remove(observer)

    def notify(self, event: str):
        for observer in self._observers.copy():
            observer.update(event)

העתקת הרשימה מונעת שינוי של הרשימה שעליה עוברים אם מנוי מסיר את עצמו במהלך ההפצה.

10. מימוש שני Observers

class LogObserver(Observer):
    def update(self, event: str) -> None:
        print(f"LOG: {event}")

class AlertObserver(Observer):
    def update(self, event: str) -> None:
        print(f"ALERT: {event}")

שני המנויים מקבלים אותו אירוע, אבל כל אחד מגיב בצורה אחרת.

מממשים מחלקה נוספת עם update ורושמים מופע שלה באמצעות attach. אין צורך לשנות את notify.

11. הרצת המערכת — חזו את הפלט

monitor = SecurityMonitor()
log = LogObserver()
alert = AlertObserver()

monitor.attach(log)
monitor.attach(alert)
monitor.detach(alert)
monitor.notify("Suspicious login")

מה יודפס למסך?

LOG: Suspicious login
ה־AlertObserver הוסר לפני ההפצה ולכן רק LogObserver מקבל עדכון.

13. מתי בוחרים Observer?

✓ כמה רכיבים עצמאיים צריכים להגיב לאירוע.
✓ רוצים להוסיף או להסיר מנויים בזמן ריצה.
✓ רוצים להימנע מתלות במחלקות תגובה מסוימות.
✓ מערכת מבוססת אירועים: UI, התרעות, לוגים, צ'אט.

מבחן הבחירה: האם אני רוצה להוסיף תגובה חדשה בלי לשנות את רכיב זיהוי האירוע?

14. מתי לא כדאי להשתמש?

✗ יש מגיב יחיד וקבוע וקריאה ישירה פשוטה וברורה.
✗ נדרש סדר תגובות קשיח עם תלות בתוצאה של כל שלב.
✗ נדרש תור עמיד, שליחה בין שרתים או הבטחת מסירה — Observer מקומי לבדו אינו מספיק.
מימוש סינכרוני: Observer איטי מעכב את הבאים אחריו; חריגה לא מטופלת יכולה לעצור את ההפצה. בתכנון מתקדם נדרש טיפול בשגיאות ולעיתים תור אירועים.

15. Observer לעומת תבניות אחרות

הבעיההתבנית המתאימה

תבניות יכולות להשתלב באותה מערכת. הבחירה תלויה בבעיה המדויקת.

16. שאלות הבנה — בחרו תשובה

17. זיהוי תבנית מתוך תרחיש

מערכת מזהה קובץ חשוד. רכיב אחד שומר תיעוד, רכיב אחר שולח התראה, ורכיב שלישי מעדכן ממשק. צוות הפיתוח רוצה להוסיף תגובות בלי לשנות את מנגנון הזיהוי.

Observer. מנגנון הזיהוי הוא Subject; התגובות הן Observers. ניתן להוסיף מנוי חדש באמצעות הרשמה, בלי לשנות את קוד הזיהוי.

שאלת המשך: אם במקום זאת נרצה לבחור בין שני אלגוריתמים לזיהוי קובץ חשוד — איזו תבנית תתאים? Strategy.

18. אתגר ניתוח קוד: מה עלול להשתבש?

def notify(self, event):
    for observer in self._observers:
        observer.update(event)

אחד ה־Observers מבצע בקשת רשת איטית, ואחר מעלה חריגה. מה יקרה למנויים הבאים?

במימוש סינכרוני המנויים מופעלים בזה אחר זה: המנוי האיטי מעכב את השאר, וחריגה שלא נתפסה עוצרת את הלולאה. אפשר לשקול טיפול נקודתי בחריגות, תור משימות או ביצוע אסינכרוני — בהתאם לדרישות.

19. משימת יישום: צ'אט רב־משתמשים

תכננו שרת צ'אט שבו אירוע user_joined מפעיל מספר תגובות.

1. הגדירו Subject עם attach / detach / notify.
2. הגדירו שלושה Observers: לוג, סטטיסטיקה והודעה למנהל.
3. הוסיפו Observer רביעי בלי לשנות את Subject.
4. שרטטו UML והסבירו מדוע בחרתם Observer.
בפרויקט עם סוקטים, Observer מארגנת את תגובות רכיבי השרת; העברת ההודעות ברשת עדיין נעשית באמצעות מנגנון התקשורת.
