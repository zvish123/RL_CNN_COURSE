מחשב תוצאה

הלקוח מבקש שירות. השרת מקבל את הבקשה, מפעיל לוגיקה ומחזיר תשובת HTTP. הלקוח אינו חייב לדעת כיצד ההצפנה ממומשת.

API = ממשק המאפשר לתוכנות לפנות לשירות. REST הוא סגנון ארכיטקטוני; כאן נלמד ממשק HTTP פשוט בסגנון REST, לא את כל אילוצי REST.
שקף 3 / חוזה API

קודם מגדירים חוזה

לפני שכותבים שרת, מגדירים מה הלקוח יכול לבקש ומה יחזור.

GET /encrypt

פרמטרים: text, team

תשובה: encrypted, id

GET /status

בדיקת זמינות ומספר בקשות שנרשמו

תשובה: ok, total

GET /log

פרמטר: since

תשובה: entries, total

למורה בלבד — כולל טקסטים מקוריים

בשרת התרגיל הקיים שלושת הנתיבים אכן ממומשים. מבחינת תכנון מערכת אמיתית, אין לחשוף את ‎/log‎ לתלמידים ללא אימות והרשאות.

שקף 5 / תגובה

מה השרת מחזיר?

HTTP/1.1 200 OK Content-Type: application/json; charset=utf-8 {"encrypted":"[12,3] [45,1]","id":7}

200 פירושו שהבקשה הצליחה. Content-Type מתאר את סוג התוכן. גוף התשובה הוא JSON.

הזוגות כאן הם דוגמה להמחשה, לא תוצאה מחושבת מהשרת.

שקף 6 / שרת ראשון

בונים שרת מינימלי ב־Python

from http.server import BaseHTTPRequestHandler, HTTPServer import json class Handler(BaseHTTPRequestHandler): def do_GET(self): if self.path == "/status": data = {"ok": True} body = json.dumps(data).encode("utf-8") self.send_response(200) self.send_header("Content-Type", "application/json") self.send_header("Content-Length", str(len(body))) self.end_headers() self.wfile.write(body) else: self.send_error(404, "Not found") HTTPServer(("127.0.0.1", 8000), Handler).serve_forever()

שמרו בשם mini_server.py, הריצו python mini_server.py, ופתחו http://127.0.0.1:8000/status.

למורה: הדגמה חיה

התחילו מ־/status. בקשו לנחש מה יקרה ב־/unknown. הסבירו ש־127.0.0.1 מאפשר גישה רק מהמחשב המקומי; שרת התרגיל המקורי מאזין לכל הממשקים.

שקף 11 / תכנון לפני קוד

המשימה שלכם: תכננו Endpoint חדש

הוסיפו לשירות שלכם GET /about, המחזיר JSON עם שם השירות וגרסתו. לפני כתיבת קוד, תכננו את החוזה ואת הפסאודו־קוד.

דוגמת כיוון למורה

GET /about → 200, גוף לדוגמה {"name":"Cipher API","version":"1.0"}. אין צורך בפרמטרים. ניתן לממש זאת על בסיס mini_server.py. אל תציגו פתרון לפני שהתלמידים תכננו.

שקף 12 / בדיקות וסיכום

איך מוכיחים שהשרת עובד?

בדיקה תקינה

GET /status → 200 ו־JSON תקין.

בדיקה שגויה

GET /unknown → 404.

קלט חסר

GET /encrypt בלי text → 400.

בדיקת לקוח

אפשר לפנות לאותו API גם בדפדפן וגם ב־requests.

שרת API = חוזה בקשה/תשובה + ניתוב + לוגיקה + המרת נתונים + טיפול בשגיאות.

למורה: הרחבה חשובה

בשרת התרגיל המקורי GET /encrypt יוצר תוצאה חדשה ורישום בלוג, ולכן יש לו תופעות לוואי והוא אינו מתאים במלואו לסמנטיקה המקובלת של GET. במערכת שתתוכנן מחדש עדיף POST /encrypt עם גוף JSON. בנוסף, /log חושף טקסטים מקוריים ויש להגביל אותו למורה בלבד. http.server מתאים להדגמה ולמעבדה מבוקרת, לא לשרת ייצור.
